Credits and money

How it works

  • £1 = 1 credit. Stripe. Multiple credit packages to buy.
  • Credits come off when the file is sent in, not when it goes back.
  • Price varies by what is selected – base solution plus options, some options included free with certain stages. Your example: Stage 1 diesel 50 credits with free deletes, dpf egr 40, dpf egr scr 45.
  • Price can still move after submission using Raise a charge and Apply credit.
  • Refunds go to the credit balance, never back out through Stripe.
  • VAT applies to new invoices only – never retrospectively, or invoices your customers already hold would silently change.
No automatic refunds anywhere. A bot failure is a handover, not a failure – no match drops into the tech queue as manual work and the credits stay taken. Credits only return when one of you clicks refund. On Void you get a yes/no prompt so it is a decision each time rather than a silent default.

What the customer never sees

The bot’s own states – VersionNotFound, PostProcessing, WaitForFinish – stay internal. The customer only ever sees Pending, Returned or Void. A file that falls through to manual work simply reads as still in progress, with the ETA if you have set one.

Roles

  • Admin – everything.
  • Tech – sees the customer name only, no email or contact details. No payment information, no gateway settings. Can refund a file.
  • Customer – own files, own balance, own invoices.

ECU notes and return instructions

Internal notes – for your techs

  • Attached to the ECU type, because that is where repeat mistakes live. Select MD1CS003 and the note for it appears.
  • Pinned at the top of the order before the tech starts. Also shows on the bot’s no-match queue.
  • Normal or warning flag, so “never use bench on this one” shows red.
  • The point of it, in your words: stop using the wrong software on an ECU.

Customer instructions – the M13 piece

  • File goes back for adblue or dpf, the portal tells the customer Reset Adblue, Reset DPF, disconnect the adblue ECU or pull the fuse, with the right video attached – worked out automatically instead of you picking it.
  • Two levels. A general rule per solution (DPF off always says Reset DPF, general video), then an ECU-specific override on top (MD1CS003 + SCR delete says pull the fuse, own video). The override wins where it exists.
  • One level would mean an entry for every ECU and solution combination you handle – thousands, and it would never get filled in.
Where it cannot be automatic. The upload page has a “vehicle not listed” route. On those the portal never learns the ECU, so no instructions attach themselves and the tech picks them by hand, as you do today.

Which WinOLS client gets searched

Your several “databases” are separate clients inside one WinOLS, not separate databases. That keeps it simple – one WinOLS instance, the bot switches client and searches again. Four clients is four searches per file, which at 10–20 files a day costs nothing.

How the search runs

  • You order the clients in the portal by dragging them. Not hardcoded, change it whenever.
  • A high bar is set – 95% to start. The bot searches in your order and the first client to clear that bar wins.
  • If nobody clears it, the bot does not settle for the first mediocre hit. It searches all of them, pools the candidates, and shows them ranked by match with the client name against each. Your tech picks.
  • That is the same VersionNotFound screen as the demo, with a client column added.
Why not strict priority. Stopping at the first hit in your top client means a 78% match there beats a 96% match in the fourth one. That is how you end up building on the wrong base file. Priority decides between good matches; the match percentage decides when nothing is clearly good.

Duplicates across clients

  • Matched on content, not names – names never line up across clients.
  • Same original: the file is hashed. Byte-identical originals collapse into one row with an “in 3 clients” badge instead of three rows you compare by eye.
  • Same mod: WinOLS gives the changed areas of a project against its original. That change set is hashed, so two solutions touching the same addresses with the same bytes are provably the same mod and show once.
Near-identical is never merged automatically. A different software version on the same ECU looks like a duplicate and is not. Those are flagged “looks similar” and stay as separate rows for a person to decide. Merging them is the same mistake as stopping at the first mediocre match.

Tools and serial numbers

Magic uses the tool serial number as the decryption key, so a file cannot be decrypted from the file alone – the bot has to know whose tool it came off. This sits inside M7, no extra charge.

How it works

  • Each customer account holds a list of their tools – Autotuner, Magic, KESS, CMD – with the serial for each.
  • On upload the customer picks which tool the file came from.
  • The bot decrypts with that serial and re-encrypts with the same one, so the file goes back into the tool it came out of. Three Magic tools on one account means it has to return to the right one.
  • A file that will not decrypt with any serial on that account drops into your manual queue with the reason written on it, rather than sitting there looking broken.
Serials are treated as secrets, because that is what they are – a decryption key. Stored encrypted, masked in the interface down to the last four, and techs do not see them at all. Same handling as payment details.

How it is put together

Windows VM

  • WinOLS 5 + OLS530, your .ols client folders, the Lua script running permanently, my local agent, Autotuner software.
  • Must auto-login to a real desktop session – WinOLS only takes the Lua script as a launch parameter, so it can never run as a Windows service.
  • Autotuner master tool passed through over USB.

Linux VM

  • Portal, database, Cloudflare Tunnel.

Traffic

  • The agent polls the portal over HTTPS, writes ticket files, Lua picks them up, and Lua posts the finished file back.
  • All outbound. No ports opened on the Windows VM, no static IP needed.

Risks I am watching

WinOLS auto-updates. An update restarts WinOLS and the Lua script does not come back, because it is a launch parameter. The queue then stalls silently. The watchdog has to spot a running-but-scriptless instance, not just a dead one.
Your Windows VM is a stealth VM. If a tool or Windows update re-detects the hypervisor, the decrypt step starts failing quietly. A health check flags it on the admin panel instead of letting files pile up looking normal.
Autotuner in a VM is the one real unknown. USB passthrough itself is proven on your box. The risk is the tool software refusing to run in a VM. Test it by decrypting a real slave file inside the VM, not by checking Device Manager – and do it before M7 is paid for.
Home broadband. A power cut or an ISP outage takes the customer portal down. Cloudflare Tunnel handles reachability, but if that matters the portal can sit on a cheap VPS and talk back over Tailscale. Same build either way, decide later.
